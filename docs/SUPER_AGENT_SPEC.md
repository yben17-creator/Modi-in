# אפיון: סופר אייג'נט ל-EVI

28 בנובמבר 2026 · עודכן אחרי בדיקה מול הקוד באותו יום (ראו "תיקונים מול הקוד" בסוף)

## מטרה ועקרונות

הסופר אייג'נט מקבל כל לילה את 20 המועמדות המובילות מהסינון הקיים, מנתח כל אחת בצוות של אייג'נטים מומחים, ומחזיר לאפליקציה הערכה אחת מנומקת: האם המצב בפועל טוב מציפיות השוק לפני הדוח הקרוב. ההחלטה לקנות נשארת אצלך.

עקרונות מחייבים:

- **אפס עלות נוספת.** לא Claude API, לא קרדיטים של Lovable, לא תוכניות API בתשלום. רק המנוי הקיים ל-Claude, Lovable Cloud הקיים, GitHub Actions בחינם, ו-SEC EDGAR, Finnhub ו-Tiingo בתוכניות החינמיות.
- **נתונים אמיתיים בלבד.** נתון חסר מוצג כחסר, ואייג'נט שאין לו נתון אומר "לא ידוע" ולא מנחש.
- **הקוד מחשב, האייג'נט שופט.** כל מספר (יחסים, ציונים, תמיכה) מחושב בקוד דטרמיניסטי. האייג'נט קורא את התוצאות, מצליב ומנמק.
- **הכנסה בלבד למסד הנתונים.** האייג'נט מוסיף ממצאים ולא מוחק או משנה נתונים קיימים.
- **בנייה בשלבים, עם מדידה מול הבקטסט** לפני שסומכים על ההמלצות.

## עקרון העלות

המוח של הסופר אייג'נט רץ כריצת Claude מתוזמנת על המנוי שלך, כמו הריצות השעתיות שכבר בנו את הפרויקט. כך הוא משתמש במכסה שכבר שילמת עליה, ולא ב-Claude API שמחויב בנפרד לפי טוקנים.

| דרך להריץ את האייג'נט | עלות נוספת | מסקנה |
| --- | --- | --- |
| Claude API מתוך Edge Function באפליקציה | תשלום לפי שימוש, נפרד מהמנוי | נפסל |
| ה-AI המובנה של Lovable | צורך קרדיטים | נפסל |
| ריצת Claude מתוזמנת על המנוי הקיים | אפס, בתוך מכסת המנוי | **נבחר** |

המחיר של הבחירה הזו: אין תשובה מיידית בתוך האפליקציה. בקשה שתשלח מהאפליקציה (למשל "נתח את AMD") נכנסת לתור ומטופלת בריצה השעתית הבאה. לשאלות דחופות אפשר תמיד לשאול אותי כאן בצ'אט, גם זה בתוך המנוי.

## ארכיטקטורה

```

          ↓
[קיים] מנוע הניתוח ב-TypeScript (earnings-insight/src/lib/engine — pitSnapshot: דירוג · חיזוי Guidance · נרות ונפח)
          ↓

          ↓
[חדש]  מאסטרו — ריצת Claude מתוזמנת על המנוי
         ├ אודיטור  ├ דלתא  ├ אורקל  ├ ראדאר  └ נמסיס
          ↓
[חדש]  מסקנות ב-Modi-in/verdicts/ → מאסטרו עצמו מכניס ל-Lovable Cloud (הכנסה בלבד, כמו ה-AI analyst) → [חדש] שופט (בקטסט ומעקב) → מעדכן משקלות למאסטרו
```

הנתונים זורמים מלמעלה למטה כמו היום. החדש מתחיל אחרי מנוע הניתוח: תיק חברה, צוות האייג'נטים, ומסקנות שחוזרות לאפליקציה. שופט סוגר את הלולאה ומעדכן כמה משקל לתת לכל מומחה.

## האייג'נטים

שבעה אייג'נטים עם שמות: מתאם אחד, חמישה מומחים ושופט שבודק את כולם. שניים מהם כבר קיימים בפרויקט ומקבלים רק שם ותפקיד. כל אייג'נט הוא קובץ הנחיות משלו ב-`Modi-in/agents/<שם>.md`, ורואה רק את החלק של תיק החברה שרלוונטי לו.

| שם | תפקיד | השאלה שלו | משתמש במה שכבר קיים | פלט |
| --- | --- | --- | --- | --- |
| **מאסטרו** (Maestro) | מתאם | מה השורה התחתונה על המניה? | הריצה המתוזמנת של Claude, מחליף את ה-AI analyst הלילי | ציון 0–100, רמת ביטחון, סיכום בעברית |
| **אודיטור** (Auditor) | פונדמנטלי | האם העסק בריא ומשתפר? | ציוני הבריאות הפיננסית והדגלים האדומים ממנוע הניתוח (SEC EDGAR) | מגמה + 3 ראיות מספריות |
| **דלתא** (Delta) | ציפיות | האם המצב בפועל טוב מהקונצנזוס? | הערכות האנליסטים מ-Finnhub שכבר נטענות | פער משוער מול ציפיות |
| **אורקל** (Oracle) | חיזוי Guidance | האם התחזית הקדימה תהיה חזקה? | מנוע חיזוי ה-Guidance הקיים | חזק / ניטרלי / חלש + נימוק |
| **ראדאר** (Radar) | גרף ונפח | מה הכסף עושה במניה? | שכבת הנרות והנפח על מחירי Tiingo | תמיכה, יעד מכירה, איסוף/פיזור שקט |
| **נמסיס** (Nemesis) | ספקן | למה ההמלצה שגויה? | כל הממצאים של המומחים (חדש) | עד 3 טיעונים נגדיים + חומרתם |
| **שופט** (Referee) | מבקר איכות | מי צדק בפועל? | מנוע הבקטסט של 3 השנים ותוצאות דוחות אמיתיים | אחוז פגיעה לכל אייג'נט והצעות שיפור |

כששני מומחים סותרים (למשל אודיטור חיובי וראדאר מזהה פיזור שקט), מאסטרו מוריד את רמת הביטחון ומציין את הסתירה במפורש, במקום למצע. שופט לא משתתף בניתוח עצמו, ולכן הוא יכול לבדוק את כולם בלי לבדוק את עצמו.

## חיבור למה שכבר קיים ורץ

שום דבר קיים לא נכתב מחדש. הסופר אייג'נט מתיישב מעל הצינור הקיים, קורא את התוצרים שלו, ומוסיף שכבת שיפוט מעליו.

| רכיב קיים | מה משתנה |
| --- | --- |
| סריקות GitHub Actions המתוזמנות (`scheduled-scan.yml`, `universe-scan.yml`, `foreign-6k.yml`) — קוראות ל-`/api/cron-*` של האפליקציה | לא משתנה. **כרגע לא פעילות**: חסרים `SCAN_CRON_TOKEN` ו-`APP_URL` ב-GitHub (DECISIONS_NEEDED #3); הסריקה האחרונה במסד היא מ-15.11 (65 חברות). התיק לא תלוי בהן |
| מנוע הניתוח ב-TypeScript (`earnings-insight/src/lib/engine`, רץ גם בשרת האפליקציה וגם ב-GitHub Actions) | לא משתנה. `pitSnapshot()` מחשב את כל הציונים; הבונה של התיק משתמש בו ישירות, כי **במסד נשמרים רק המדדים הבסיסיים** (בריאות ויחסים), לא מנבא ה-Guidance, פער הציפיות או הנרות |
| מנוע ה-backtest (`backtest-pit-3y.yml`, `pit-run.ts`, `pit-eval.ts`) | ה-cache שלו משמש לדירוג הראשוני של התיקים בלי קריאות API; רק 20 המובילות מרועננות |
| מנוע חיזוי ה-Guidance | לא משתנה. הפלט שלו נכנס לתיק ואורקל מפרש אותו |
| שכבת הנרות והנפח | לא משתנה. הפלט שלה נכנס לתיק וראדאר מפרש אותו |
| ה-AI analyst הלילי (משימה מתוזמנת "EVI AI analyst (nightly)", מושהית מ-22.11) — מכניס שורות `ai_note` ל-`financial_metrics` דרך כלי ה-SQL של Lovable | משודרג למאסטרו. אותה ריצה מתוזמנת, אותה הרשאה (הכנסה בלבד) |
| מנוע הבקטסט של 3 שנים | לא משתנה. שופט משתמש בו למדידה |
| אפליקציית Lovable המפורסמת | מתווספים כרטיס "דעת הצוות" במסך המניה וכפתור "בקש ניתוח" |

**תיק חברה (dossier).** קובץ JSON אחד לכל מועמדת, שנבנה בקוד מהנתונים שכבר נטענו ונשמר ב-`earnings-insight/dossiers/<תאריך>/<טיקר>.json` (ה-workflow יכול לכתוב רק למאגר שלו בלי טוקן אישי; מאסטרו קורא משם). הקוד: `src/lib/engine/dossier.ts` ו-`src/lib/dossier-run.ts`. הוא מכיל את תוצאות כל המנועים הקיימים, כבר מחושבות. האייג'נטים קוראים רק את התיק, ולכן לא צריכים גישה לרשת, לא שורפים מכסת API ועולים מעט טוקנים.

**הדרך חזרה לאפליקציה.** מאסטרו כותב את המסקנות כקובץ ל-`Modi-in/verdicts/`. בשלב 4 הוא גם מכניס אותן בעצמו ל-Lovable Cloud דרך כלי ה-SQL של Lovable (`query_database`, הכנסה בלבד, לא צורך קרדיטים), בדיוק כמו ה-AI analyst היום. ל-GitHub Actions אין גישה למסד: מפתח השירות מנוהל ב-Lovable ולא שמור ב-GitHub.

## מודל נתונים וממשק באפליקציה

**תיקון: בלי טבלאות חדשות.** שינוי סכמה נעשה רק דרך Lovable (כך מחייב `AGENTS.md`), וזה צורך קרדיטים — בניגוד לעקרון העלות. במקום זה משתמשים בטבלה הקיימת `financial_metrics`, בדיוק כמו ה-AI analyst (שורות `ai_note` / `ai_request`). אין שינוי סכמה, ולכן אין צורך באישור הזה.

| במקום | שורה ב-`financial_metrics` | מי כותב |
| --- | --- | --- |
| `agent_requests` | `metric = ai_request` (קיים: `ai-request.server.ts`, כפתור הבקשה כבר קיים במסך החברה) | האפליקציה (אתה) |
| `agent_findings` | `metric = agent_finding`, `model_version = super-agent-v1`, `inputs` = JSON של הממצא | מאסטרו (הכנסה בלבד) |
| `agent_verdicts` | `metric = agent_verdict`, `model_version = super-agent-v1`, `value` = הציון, `inputs` = ביטחון, סיכום, מועד דוח; התוצאה בפועל = שורה נוספת `agent_outcome` | מאסטרו; שופט מוסיף `agent_outcome` |

הטבלה המקורית שהוצעה (לתיעוד בלבד):

| טבלה | מה נשמר בה | מי כותב |
| --- | --- | --- |
| `agent_requests` | בקשות ניתוח מהאפליקציה: טיקר, מועד, סטטוס | האפליקציה (אתה) |
| `agent_findings` | ממצא של כל מומחה: אייג'נט, טיקר, מגמה, ראיות, תאריך | הסריקה מ-verdicts/ |
| `agent_verdicts` | המסקנה של מאסטרו: ציון, ביטחון, סיכום, מועד הדוח, ואחר כך התוצאה בפועל | הסריקה; שופט משלים את התוצאה |

במסך המניה באפליקציה נוספים שני דברים:

- **כרטיס "דעת הצוות"**: הציון של מאסטרו, שורה אחת מכל מומחה, הטיעונים של נמסיס, ואחוז הפגיעה ששופט מדד למאסטרו עד כה.
- **כפתור "בקש ניתוח"**: כבר קיים (`requestBusinessModel` ב-`ai.functions.ts`) ומכניס `ai_request`. התשובה מגיעה בריצה הבאה.

## תקציב מכסה ובקרות

המשאב המוגבל הוא מכסת המנוי של Claude, ולכן כל הכללים כאן נועדו לשמור עליה.

- **סינון זול קודם.** רק 20 המובילות בדירוג הקיים, ורק כאלה שהדוח שלהן ב-30 הימים הקרובים, מגיעות למאסטרו. המספר 20 ניתן לשינוי.
- **ריצה אחת בלילה לניתוח המלא,** וריצות קצרות שעתיות רק כשיש בקשות בתור. תור ריק = ריצה שנגמרת מיד.
- **לא מנתחים פעמיים.** חברה שהתיק שלה לא השתנה מאז הניתוח הקודם מדולגת.
- **נמסיס רק על מועמדות עם ציון גבוה,** שם טעות עולה הכי הרבה.
- **עצירה במכסה.** אם המכסה נגמרת באמצע ריצה, החברות שלא נותחו נשארות בתור לריצה הבאה. אין מעבר אוטומטי לתשלום.
- **הפיתוח עצמו קודם.** אם ריצות הפיתוח השעתיות פעילות במקביל, מאסטרו רץ פעם בלילה בלבד עד שהפיתוח נגמר.

שאלה פתוחה: כמה מניות בפועל נכנסות בריצה לילית אחת בלי לפגוע בעבודת הפיתוח. נמדוד את זה בשלב 1 ונעדכן את ה-20.

## מדידה ובקטסט

הסופר אייג'נט נחשב מוצלח רק אם שופט מראה שהוא מנבא טוב יותר מהדירוג הקיים על אותן חברות. 55% פגיעה לא מספיק.

1. **בקטסט עיוור.** שופט מריץ את מאסטרו על תיקים היסטוריים מתוך מנוע הבקטסט, שנבנו רק מנתונים שהיו ידועים לפני הדוח. כך אין דליפה מהעתיד.
2. **דגימה קטנה.** בגלל המכסה, בכל לילה שלא נדרש לניתוח חי נבדקים 10 דוחות היסטוריים נוספים, עד שמצטברים מאות.
3. **מעקב חי.** אחרי כל דוח אמיתי, שופט משלים ב-`agent_verdicts` מה קרה בפועל.
4. **ציון לכל אייג'נט.** שופט מודד את אחוז הפגיעה של כל מומחה בנפרד. מומחה שלא מוסיף ניבוי מקבל משקל נמוך אצל מאסטרו.
5. **דוח שבועי בעברית** עם התוצאות והצעות שיפור להנחיות של האייג'נטים. זו לולאת השיפור העצמי שביקשת.

## שלבי בנייה

חמישה שלבים. כל שלב עובד לבד ומוסיף ערך גם אם עוצרים אחריו.

1. **תיק חברה.** workflow ידני `Dossiers` ב-GitHub Actions שכותב תיקים ל-20 המובילות מתוך המנועים הקיימים. אין שינוי במסד הנתונים. (נבנה 28.11.)
2. **אודיטור + מאסטרו בסיסי.** ריצה לילית שכותבת מסקנות ל-`verdicts/` בריפו בלבד. כאן מודדים כמה מכסה ריצה אחת צורכת.
3. **כל הצוות.** דלתא, אורקל, ראדאר ונמסיס מצטרפים.
4. **חיבור לאפליקציה.** שורות `agent_verdict` / `agent_finding` ב-`financial_metrics` (בלי טבלאות חדשות) וכרטיס "דעת הצוות". דורש אישור שלך (כתיבה למסד ופריסה).
5. **שופט.** בקטסט עיוור, מעקב חי ודוח שבועי. מכאן מחליטים לפי המספרים אם לסמוך על מאסטרו.

## נקודות אישור וסיכונים

שלבים 1–3 לא דורשים אישור כי הם לא עולים כסף ולא נוגעים במסד הנתונים. אלה הנקודות שבהן אעצור ואבקש אישור:

- [ ] אישור האפיון הזה ושמות האייג'נטים
- [ ] הפעלה מחדש של הריצה הלילית המתוזמנת (כרגע מושהית)
- [ ] ~~שלוש הטבלאות החדשות~~ — בוטל: שימוש ב-`financial_metrics` הקיימת, בלי שינוי סכמה
- [ ] כתיבת שורות `agent_verdict` / `agent_finding` למסד (הכנסה בלבד)
- [ ] פריסת השינויים באפליקציה לפרודקשן

סיכונים:

- **מכסה.** אם המכסה לא מספיקה ל-20 מניות, מקטינים ל-10 ומנתחים רק עם דוח קרוב. לא עוברים ל-API.
- **זמן תגובה.** בקשת ניתוח מהאפליקציה עונה תוך עד שעה, לא מיד.
- **ביטחון יתר.** טקסט מנומק יכול לשכנע גם כשהוא שגוי. לכן אחוז הפגיעה של שופט מוצג תמיד ליד הציון.
